# AI 工作台与自定义 Agent：对话性能优化方案（待评估）

本次只提交方案，尚未实施以下性能改动。检查基于 2026-09-29 本地代码；没有线上请求追踪、生产压测或实际模型首字耗时数据。建议先做执行入口精简查询，再依据分阶段耗时决定是否改工作区文件同步。

## 已确认的路径与建议

| 优先级 | 现状与影响 | 建议 | 验收方式 |
| --- | --- | --- | --- |
| 第一批 | `backend/agent_service.py:1348` 的排队入口及 `:1639` 的执行入口直接查询 Agent；模型默认 `selectin` 会连带加载全部会话和多个资源关联。会话越多，单次启动搬运的数据越多。详情接口的所有权检查已使用轻量查询，执行入口尚未对齐。 | 在这两个入口按需加载；只查询当前会话和实际运行资源。避免全局修改 ORM 默认加载方式。 | 拥有 1/100/1000 个会话时，启动查询不加载全部历史会话；会话对象数、数据库返回字节不随会话总数增长。 |
| 第一批 | `execute_agent_turn` 在异步函数中直接执行同步数据库查询、刷新和提交；同一服务进程内会阻塞其他对话的事件发送。现有文件准备已经转到线程，这部分无需重复改造。 | 将“准备运行输入”“保存阶段结果”等封装为短事务函数，在工作线程中创建、使用并关闭自己的 Session，返回普通数据。禁止把同一个 Session 或懒加载 ORM 对象在线程间共享。 | 20 个并发用户，模拟数据库单次查询延迟 50ms：事件循环延迟 P95 < 50ms、无跨线程连接错误；这是目标，尚未实测。 |

## 本地查询对照

环境：当前 Python 3.11、SQLAlchemy、SQLite 内存库；单个智能体具有 1000 个历史会话；每组 7 次，清空 Session 对象后重查，记录 SQL 数量、被加载会话数和耗时中位数。

| 读取方式 | SELECT 次数 | 加载会话对象数 | 中位耗时 |
| --- | ---: | ---: | ---: |
| 执行入口当前的普通 Agent 查询 | 7 | 1000 | 13.31ms |
| 现有 `_get_agent_or_404` 轻量查询 | 1 | 0 | 0.27ms |

这证明额外加载确实存在，不能将上述比值作为整次对话或线上首字速度的提升承诺。模型请求、工具调用及文件操作仍需独立测量。

## 建议实施顺序

1. 增加排队、数据库准备、工作区准备、模型首事件、模型结束、工作区回收、计费结算的分阶段耗时。只记录运行编号及数值，不记录凭据、提示词正文或用户文件内容。
2. 精简运行入口查询，合并重复控制轮询，拆分异步函数内的阻塞数据库阶段。预计 2–3 人日，含故障回归；上线前若时间紧，先仅做查询精简与测量。
3. 根据实际文件准备与历史加载占比，再评估第二批；文件同步改造单独估时，不与前三项功能修复捆绑上线。

压测矩阵：工作台/智能体 × 平台/自定义模型 × 1/5/20 用户 × 短/长历史。分别记录排队时间和执行时间；同一用户超出并发上限的排队不能算作模型变慢。

保留现有 Redis 流回放、断线继续执行、流快照压缩以及前端 50ms 合并渲染。代码没有逐 token 写 MySQL；仍存在上表列出的控制轮询，不需要为本轮性能优化整体重写流式架构。
