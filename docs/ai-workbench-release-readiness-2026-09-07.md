# AI 工作台上线评估

评估日期：2026-09-07。代码基线：`367ddbf`。

## 结论与范围

当前版本已有完整的主要操作界面和相当一部分后端保护，但尚未达到正式交付上线标准。建议继续使用隔离测试环境验收，先修复安全和计费阻断项，再开展内部灰度。

本次检查覆盖 AI 工作台、专家对话、初始化、历史列表、流式响应、模型选择、趣点、内容预览、公开资源及部署保障。公开提示词、图片上传和公开 MCP 虽然不全在对话页面内，但与工作台共用身份或资源，直接影响其上线安全。

本次依据当前代码重新核实，没有把历史审计文档的结论直接当作现状。未修改业务代码，未连接生产数据库、调用真实模型或读取真实凭据。下面的复现均使用内存数据库、模拟响应或无害测试标记。

本文的 P0 表示上线安全阻断；P1 表示交付前必须处理的高影响问题；P2 表示近期产品与可靠性改进。它们不是对生产环境已经发生事故的断言。

## 已确认问题

### R1 / P0：HTML 预览没有隔离登录态

- 位置：`frontend/src/views/admin/components/HtmlPreviewCard.vue:48`、`frontend/src/utils/html-preview.js:74`、`frontend/src/stores/auth.js:127`。
- AI 回复中的 HTML 通过 `srcdoc` 渲染，同时启用 `allow-scripts` 和 `allow-same-origin`。脚本内容被保留，预览默认打开，进入可视区域后自动加载。
- 同源脚本可以访问父页面及其存储；access token 和 refresh token 存在 localStorage。因此不可信模型输出、工具返回内容或分享内容可能获得工作台登录权限。
- 验证：无害 HTML 脚本被实际内容解析器识别为预览，并被实际预览构造函数完整保留。未在用户登录页面执行脚本或读取真实 token。
- 修复方向：使用独立来源承载不可信 HTML，或使用不具备同源能力的沙箱；需要访问业务数据时通过受限消息协议或服务端代理，不能把整个登录态开放给预览。
- 验收：恶意测试页面不能读取父页面 DOM、localStorage，不能自行移除沙箱或利用父页面身份调用管理接口；普通对话和公开分享都覆盖。

### R2 / P0：提示词和图片上传仍存在主动内容入口

- 位置：`frontend/src/views/public/PublicPromptTemplateDetail.vue:70`、`frontend/src/views/admin/PromptTemplateDetail.vue:85`、`backend/main.py:1028`。
- 公开提示词使用 `v-html` 展示内容，只替换变量标记，没有先转义或清洗 HTML。
- 图片上传只检查客户端声明的 `image/*`，保留用户文件扩展名，再通过静态目录提供访问。攻击者可以声明图片类型并上传 HTML 等主动内容；封面上传也有同类逻辑。
- 影响：不需要借助模型生成恶意内容，也可能形成持久化脚本执行入口。与同源存储登录令牌组合后，影响超出上传者本人。
- 修复方向：提示词按文本转义后再高亮变量；图片校验真实格式、解码重编码、固定安全扩展名；主动内容从独立来源提供或强制下载。实际部署的 CSP 和静态响应头也需核验。
- 验收：脚本、事件属性和伪装图片均无法在工作台来源执行。

### R3 / P0：全平台用量仍有无鉴权接口

- 位置：`backend/dashboard_routes.py:341`。
- `/api/public/token-usage` 没有认证依赖，直接复用全局汇总查询，返回用户邮箱和用量。
- 验证：在独立 FastAPI 应用中挂载实际路由，以模拟数据替换查询，未携带身份即可得到 HTTP 200 和逐用户数据。
- 生产是否已经暴露该地址需要核验网关；代码层本身没有防护，不能按安全通过验收。
- 修复方向：移除公开入口，或改为明确授权的服务接口；确需公开的数据必须为不可识别用户的汇总数据。
- 验收：匿名、普通用户和授权管理员分别验证可见范围。

### R4 / P1：公开 MCP 配置脱敏不完整

- 位置：`backend/main.py:1072`。
- 当前只覆盖 `headers`、`env` 字典。URL 查询参数、连接串或命令参数中的凭据会原样返回。
- 验证：实际脱敏函数会隐藏模拟 Authorization 值，但保留模拟 URL token 和 `--api-key` 参数。
- 修复方向：公开的是无凭据安装模板，用户实例配置与秘密字段分开保存；采用可公开字段白名单，避免仅靠敏感字段名猜测。
- 验收：对支持的 MCP 配置格式使用测试秘密值扫描公开列表、详情及导出结果，确认无残留。是否存在历史实际泄露需要另行盘点。

### R5 / P1：模型连接失败可能导致趣点一直冻结

- 位置：`backend/model_gateway.py:168`、`backend/credit_billing.py:198`、`backend/credit_billing.py:305`、`backend/credit_billing.py:375`。
- 请求开始时增加 `request_count`；上游连接失败时 `abort_gateway_request` 仅清除进行中标志，不记录对应的最终事件。
- 结算要求用量事件数量达到请求数量。失败请求缺少事件，运行会一直停留在 `pending_reconciliation`。
- 验证：内存数据库中预占 10.00 趣点，模拟一次连接失败，执行结算及三次对账后，10.00 仍处于冻结状态。
- 修复方向：为每次请求记录可幂等终结的状态，区分确定未调用成功和用量未知；补齐连接异常、超时、取消和进程崩溃的补偿及人工核查入口。
- 验收：连接失败不产生永久冻结；不重复计费；有真实用量时不得简单当作零费用释放。

### R6 / P1：历史会话的固定模型与默认模型冲突

- 位置：`frontend/src/views/admin/AgentChat.vue:1261`、`frontend/src/views/admin/AgentChat.vue:1266`、`backend/enterprise_routes.py:629`、`backend/agent_routes.py:1367`。
- 前端选择历史会话后，先读会话模型，随后又覆盖为助手默认模型。
- 管理员发布新的默认模型后，bootstrap 将助手绑定模型替换为只含新模型的列表；旧会话固定的模型又可能被后端判为未绑定。
- 验证：实际前端选择函数将固定模型 2 重置为默认模型 1。在内存数据库模拟默认模型变更后，发送模型 1 得到 409；改发历史模型 2 仍得到 400。
- 修复方向：明确历史会话模型的兼容与退役策略。前端、后端授权及配置发布保持同一规则；不可只修复显示值。
- 验收：新会话使用新默认模型，已有会话可按约定继续；历史模型被禁用时有明确迁移或新建入口。

### R7 / P2：历史搜索只搜索已经加载的分页

- 位置：`frontend/src/views/admin/components/ChatSidebar.vue:129`、`backend/agent_routes.py:950`。
- 搜索只过滤当前 `sessions` 数组，列表接口没有搜索参数。
- 例如总计 200 条但只加载 20 条，搜索更早会话可能显示“无匹配对话”。搜索后列表变短，还会使依赖滚动的下一页加载无法触发。
- 修复方向：服务端按用户、助手和搜索词查询，搜索独立分页；取消或忽略过期请求。
- 验收：未加载页中的会话能被找到；清空搜索、加载更多和快速输入不会串结果。

### R8 / P2：断线、刷新与重新进入缺少完整恢复体验

- 位置：`backend/agent_service.py:1597`、`frontend/src/views/admin/AgentChat.vue:1486`、`frontend/src/views/admin/AgentChat.vue:1819`。
- Web 执行与 SSE 生命周期绑定，连接关闭后会取消执行任务；前端重新进入主要读取消息，没有恢复活动运行及事件流的完整流程。
- 已有运行取消和部分结果持久化保护，但不能据此承诺“刷新后继续执行并接回结果”。
- 修复方向：先确定产品契约。若要求后台继续执行，运行与连接解耦并提供状态恢复和事件重放；若规定断线即取消，则明确提示取消结果和重试可能产生的外部副作用。
- 验收：慢网、断网、刷新、关闭页面、切换资源页面和后端重启分别测试；用户不应因不清楚状态而重复触发已执行的操作。

以下项目本次没有生产环境证据，需要在放行前补齐：

- 网关清除伪造身份头，后端 API 端口不能绕过网关访问；使用两个普通账号验证数据隔离。
- 数据库迁移执行记录、从旧版本升级及回滚演练。`create_all` 不会替已有表补齐新字段。
- MySQL 下并发领取、重复回调、取消和计费结算；SQLite 不验证生产行锁语义。
- 模型响应中断、Runtime 失联、租约失效、服务重启后的运行状态与冻结额度恢复。
- 启动脚本使用 nohup；需确认生产是否另有进程托管、异常重启、健康检查、日志轮转和告警。
- 数据库、用户工作区和加密密钥的一致备份及恢复演练。
- 真实浏览器自动化：登录刷新、首条消息、停止、重试、历史分页与搜索、附件、HTML 预览、分享撤销、窄屏操作。
- 目标并发下首屏时间、首个响应时间、错误率、运行排队时间和资源消耗。性能放行阈值需按实际容量约定。
- 依赖漏洞扫描与可重复构建。当前部署执行 npm install，需要确认发布流程是否锁定依赖与产物。

## 还需明确的产品边界

- 对话分享目前读取实时消息，不是创建分享时的快照，并且保留助手消息中的工具过程。应明确是否公开后续续聊、是否包含工具输出，并在创建分享时清楚表达范围。
- 历史列表首次加载失败会提示错误，但需要核验是否有足够直接的重试入口，避免看起来像“暂无对话”。
- 趣点应明确区分可用、冻结、实际消耗和待核对状态，提供可核查的流水；不能只在回复下方显示一个数字。
- 全局配置发布应说明对运行中任务、旧会话和下一次新建会话各有什么影响。

## 建议放行顺序

1. 先关闭不可信内容的同源执行、公开数据泄露和公开凭据泄露入口。
2. 修复失败结算与历史模型一致性，增加对应回归用例，修复现有失败测试。
3. 补齐历史搜索和运行恢复的产品契约，完成两账号隔离及真实 Runtime 联调。
4. 在具备监控、回滚和备份恢复证据后进行受控内部灰度，再根据错误率与使用反馈决定正式发布。

菜单、间距和加载动画已得到多轮改善。当前影响上线判断的主要问题是安全、异常状态和历史数据兼容性，而不是继续调整页面外观。
